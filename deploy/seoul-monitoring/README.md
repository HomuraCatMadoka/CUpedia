# 首尔运维告警

从首尔之外运行告警器。它使用当前运维 Mac 已有的 `ssh cupedia` 和 Codex 每 15 分钟的检查，向已连接的 Gmail 自己发送邮件。Mac 和 Codex 在线时才会执行。同时保留首尔原有面板和备份任务。告警器只读取公开页面、首尔的状态文件和食堂入库汇总，不触发业务任务。

| 告警           | 何时提示                                                                 | 第一项检查                                         |
| -------------- | ------------------------------------------------------------------------ | -------------------------------------------------- |
| 公网访问       | 首页、固定课程或 Wiki 的 HTTPS 或正文连续两轮失败                        | 从另一网络访问同一页面，再检查 Nginx 和监控面板    |
| 备份任务漏跑   | R2 03:30、PostgreSQL 04:20 还没有当天的启动记录                          | 查看对应的 systemd timer 和服务状态                |
| 备份失败或过期 | 当天任务报告失败，或 R2 04:05、PostgreSQL 05:00 还没有通过校验的成功副本 | 检查失败日志以及 `latest/manifest.json` 的成功时间 |
| 食堂同步漏跑   | 香港时间 08:57、11:57、17:57 后，最近餐次仍找不到已接受的菜单快照        | 对照 Supabase 主任务、GitHub 兜底和首尔同步日志    |

检查按香港时间计算。任务运行中给足原来的超时窗口。状态源读不出来时单独报告，避免误判任务已失败。告警按事件编号去重。投递并核对收件箱后，再确认该条已处理。默认负责人是当前连接邮箱的 CUpedia 维护者。

```sh
python3 -B deploy/seoul-monitoring/alerts.py check
python3 -B deploy/seoul-monitoring/alerts.py simulate
```

`simulate` 在独立状态目录中用两轮模拟 HTTP 503 走相同判定方式。演练邮件有“演练”标识。脚本只生成待发内容，由已有 Gmail 连接投递。用 `alerts.py ack <告警编号> <邮件编号>` 确认已送达。演练回执加 `--simulation`。真实检查和演练使用不同的状态。邮件不包含网站正文、数据库行或连接凭据。

这一步覆盖访问、关键任务和备份。容器重启、磁盘、证书到期和发布失败告警由 #939 继续跟踪。
