# Fresh-eyes 审校子代理配方（spec-compliance review）

来源：2026-08 mrtsels/trading-agents 发布流程实测。审校子代理找到 2 个可用性阻断 + 10 处修正（指标白名单 13→12、输出目录无锚点、脚本回退路径不存在、未来日期守卫缺失、内层标题污染顶层结构等），全部被采纳。**发布任何技能/文档/脚本前跑一遍。**

## 派发形态

- **review-only**：context 里明确"不要修改任何文件，不要碰 git"
- 输出写到文件（如 `/tmp/<name>_review.md`），分级：🔴 严重 / ⚠️ 警告 / 💡 建议，每条给 `[文件:行/段落]` 定位 + 说明 + 建议修法；通过项逐条 ✅；结尾总评"能否直接投入使用"
- 给足审校对象路径 + 规格（要核对什么）

## 字母清单设计（A-G 实例，按需增删）

- **A. 流程完整性**：步骤自洽（Step 0-N 全链路无缺环）；每个角色/每步有指令；产出目录结构与正文一致
- **B. 语义正确性 vs 源**：轮次/顺序/条件逻辑——**对照源仓库代码逐行核对**（审校者实读 `conditional_logic.py` 验证了辩论轮次语义）
- **C. 声明一致性**：如"零 LLM 配置"正文 vs 附录（附录需 key 属预期，不算矛盾——清单里写明）
- **D. 角色约束 vs 源 prompt**：硬性格式（如 `FINAL TRANSACTION PROPOSAL: **BUY/HOLD/SELL**`）逐文件核对行号命中
- **E. 脚本规格合规**：用法、段落结构、兜底路径、守卫——**实际运行脚本** + grep 输出结构（如 `grep -c '^## '` 应等于预期段数）
- **F. 事实准确性**：行号引用、性能声明、commit hash——读源文件核对；审校者实测了每处行号引用
- **G. 新手可跑通性**：输出目录是否有锚点（`<输出目录>` 占位符 = 模糊指令）；脚本回退路径是否真实存在；指令与可用数据是否自相矛盾（如告诉分析师选 13 个指标但上下文只有 5 个）

## 让审校有效的验证方法

1. **读源文件核行号/prompt 原文**——不只信 SKILL.md 自述
2. **运行产物**——跑脚本、数输出结构、检查 UNVERIFIED 计数
3. **查"看似合理实则不存在"的路径**——审校发现 clone 一个仓库拿不到脚本（脚本只在技能仓库里）
4. **查指令↔数据矛盾**——新手 agent 会照着做然后卡住

## 应用流程

审校报告 → 父代逐条 patch（⚠️ 全修，💡 低成本也修）→ **回归实测**（重跑脚本/测试，确认修正没引入新问题）→ commit + push → 技能侧 pull。

## Pitfalls

- 审校输出文件可能因超长行被 `read_file` 误判为 binary——用 `file` 确认 UTF-8 后 `cat` 读取
- 审校子代理 transcript 可能静默数分钟（在逐文件核验）——别急着杀进程；看 live transcript 确认在干活，同时并行做其他工作
- 子代理可能误报（如把正确的 hash 当笔误）——父代核实后再改，别盲从
