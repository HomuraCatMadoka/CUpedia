# 通知创建与来源写入保持原子，后续生命周期彼此独立

全站通知中心要把课程评论回复等业务事实投递给特定 User。若来源写入成功而通知写入失败，收件人会永久漏收；但若通知与来源长期级联，作者删除内容时又会悄然改写收件人的通知历史。通知还不能成为已删除正文的副本，否则会绕过来源上下文的删除语义。

产生通知的业务写入与通知写入在同一个数据库事务中完成；自回复等没有收件人的业务写入不创建通知。事务提交后，通知由通知上下文独立拥有：来源删除不级联删除通知，通知永久保留且只保存识别事件所需的元数据，不复制回复正文。用户打开通知时实时解析来源；来源已不存在则显示「消息不存在」。

这样，已提交的来源事件不会漏发通知，但通知写入失败会令来源写入一并失败。通知记录不能恢复或展示已删除正文，读取路径必须把来源缺失视为正常状态；数据关系也不能依赖从来源到通知的级联删除。来源上下文继续拥有业务事实，通知上下文只拥有收件人、事件引用和阅读状态。

## 异步 outbox 例外

若业务契约明确要求“通知失败不得回滚已保存的来源事件”，来源事务必须改为原子写入来源事件和 durable outbox 消息；此时 outbox 消息就是不会漏失的通知意图。独立投影器随后以消息 ID 幂等创建最小通知记录，并用 lease/retry 处理失败。投影失败不得删除来源事件或 outbox，通知读取路径可触发投影，但必须把投影失败视为暂时不可用并留待下次重试。

采用此例外的模块不得同时在来源事务创建最终通知记录，否则 outbox 会失去实际作用。Campus Map Notes 因 #722 明确要求异步、失败隔离的通知，所以采用此例外；其他模块仍遵守上面的默认原子写入规则。
