# 高德地图红绿灯倒计时：公开机制与证据边界

日期：2026-08-09
范围：回答高德倒计时是否主要由数据量学习、是否接入交管灯态/SPaT、是否使用浮动车轨迹或北斗，以及这些事实对 CUHK 校巴 ETA 的启示。本文不决定校巴模型。

## 结论

高德的公开证据支持**至少两条并存的数据路线**，不是“只从交管信号机读取”，也不是“数据够多后让一个黑箱 AI 自己猜出来”。线上如何选择或融合两条路线仍未公开：

1. 高德与阿里名下的专利明确公开了从多车 GPS/行驶轨迹中挖掘信号灯周期、红灯时长和变灯偏移的算法。其关键证据是车辆在路口前的停止、启动和通过时间在大量样本中形成的周期性分布。
2. 阿里另一项专利还公开了按时段建模、用连续多天同一时段的变灯偏移预测未来时段，并用已经产生的当日轨迹校验预测。因此“历史学习 + 新轨迹校验”都有公开技术依据。
3. 至少部分城市确实把官方信号动态/灯态数据接入高德。公开材料没有证明所有路口都这样做；专利反而把官方数据覆盖有限、更新受限作为轨迹挖掘要解决的问题。
4. 北斗/GNSS 为车辆提供时间、位置、速度与行驶方向，是生成轨迹、判断用户接近哪个路口的定位底座；没有证据表明北斗卫星本身提供信号灯相位或剩余秒数。
5. 公开来源只写“灯态数据”“信号动态数据”，没有披露接口是不是 SAE J2735 SPaT、是否由每台信号机直连，或经城市信控平台转换。因此只能确认**官方灯态接入**，不能确认**标准 SPaT 或信号机直连**。
6. 专利披露算法，不等于生产代码开源，也不能证明高德当前线上实现逐字采用某一专利。没有找到高德发布的倒计时训练代码、模型权重、数据集或完整评估集。

一句话回答：**数据量是高德“无官方灯态覆盖”路线的重要条件，但有效信息来自大量轨迹中可辨识的停止/启动周期；有官方数据的城市则会融合权威灯态。**

## 公开算法实际上怎样工作

### 1. 从启动时间分布挖掘完整信号周期

高德软件的 [CN114463969B《红绿灯周期时长的挖掘方法》](https://patents.google.com/patent/CN114463969B/zh) 描述：

- 选定一个路口和一个目标时段；
- 收集在该路口停车等待的多辆样本车轨迹；
- 找到该时段最先启动的样本车，以其启动时刻为基准；
- 计算其他车辆启动时刻相对基准的偏移；
- 对偏移量做数量分布统计，从其中的周期性确定信号灯周期；
- 同一个时段可以汇入多天的轨迹；一天也可以切成不同目标时段，以处理早晚高峰和平峰可能采用不同周期的情况。

这不是要求每辆车都观察到信号灯，而是利用“红转绿后排队车辆成批启动”在总体轨迹中的周期性。专利背景明确说，交管部门提供的周期数据覆盖范围有限，提出该方法就是为了扩大覆盖。

### 2. 从停车时长分布挖掘红灯时长

高德软件的 [CN114999143B《红灯时长挖掘方法》](https://patents.google.com/patent/CN114999143B/zh) 使用另一种统计信号：

- 从相连路段的轨迹中计算车辆在路口前的停车时长；
- 排序停车时长，寻找“正常等红灯停车”均匀分布结束后的突变拐点；
- 用拐点估计红灯时长，从而排除事故、靠边停车等异常长停留；
- 可按小时等目标时段分别挖掘，再聚合相邻、相近的时段；
- 可用预训练轨迹分类模型剔除非机动车轨迹。

专利示例图使用数千辆样本车来寻找拐点，并直接把“大数据带来更广覆盖和更好泛化”列为技术效果。这支持“数据量很重要”，但也表明**不是把所有位置点直接扔进一个模型**：先做路口、方向、停车行为、时段和异常点处理，才得到可学习信号。

### 3. 预测未来变灯偏移，并用新轨迹校验

阿里巴巴（中国）名下的 [CN114926980B《交通数据挖掘方法》](https://patents.google.com/patent/CN114926980B/zh) 更接近用户看到的倒计时流程：

- 轨迹可以是带时间、位置和速度的 GPS 数据，由道路上的通行对象回传；
- 先从路口通过量的周期性变化估计周期与变灯偏移；
- 把连续多天同一时段的偏移序列输入预训练预测模型，预测未来一天或多天同一时段的偏移；
- 模型可为神经网络或自回归模型，专利没有限定一种；
- 目标日已经发生的“先停后走”轨迹可以反推出实际变灯时间，用于校验预测偏移；
- 示例按小时切片，也明确指出可使用过去七天预测下一天。

因此，公开技术路线里确实同时存在：

```text
历史多车轨迹
→ 挖掘路口周期与时段规律
→ 预测未来变灯偏移
→ 新产生的轨迹反推实际变灯时间
→ 校验或修正预测
```

这里的“实时性较好”是专利申请人的技术效果表述，不等于公开承诺了线上延迟、准确率或更新频率。

### 4. 从 GNSS 轨迹维护灯控方向

高德云图较新的 [WO2025200516A1《灯控信息获取方法》](https://patents.google.com/patent/WO2025200516A1/zh) 把行驶轨迹定义为车载导航设备回传的 GNSS 位置序列，并按左转、直行、右转、掉头方向统计停车轨迹占比，用最近一天或最近 30 天等窗口判断某方向是否存在灯控。这进一步证明轨迹众包是持续维护路口结构信息的一条公开路线。

但该专利主要判断“某方向是否存在灯控”，不是直接输出剩余秒数；它只能作为数据管线和规模化维护的旁证。

## 官方灯态接入不是猜测，但覆盖和协议未知

官方接入至少有以下直接证据：

- 烟台市公安局 2021 年文件写明，与高德合作，将市区 235 个重点路口的“信号动态数据”通过高德推送，提供“实时灯态切换提醒”和绿波引导。见[烟台市公安局便民惠商措施 PDF，第 6 页](https://www.yantai.gov.cn/attach/0/f17780cb48bd404ebc7a8e3be506fa8e.pdf)。
- 北京市科委转载的 2023 年公开材料称，北京亦庄、西安、兰州、泉州、济宁等地公安交警机构与高德开展智能信号灯合作，并说“越来越多城市和地区的官方灯态数据接入”。材料还把北斗定位、AI、智慧交通列为共同技术基础。见[北京市科学技术委员会公开稿](https://kw.beijing.gov.cn/xwdt/kcyx/xwdtcyfz/202312/t20231207_3818080.html)。
- 泉州市公安局 2025 年对政协提案的答复更具体地写到，城市信号控制系统灯态数据与高德、百度实时共享，超过 1,000 个红绿灯实现灯态上图。见[泉州市公安局答复](https://gaj.quanzhou.gov.cn/zwgk/jyta/zxwyta/202509/t20250909_3208330.htm)。

这些来源能证明“交管官方数据会接入”，但仍不能回答：

- 高德接收的是当前灯色、剩余秒数、完整配时方案，还是三者的组合；
- 城市端是逐台信号机、区域信控平台还是政务数据平台提供；
- 接口是否使用 SAE J2735 SPaT、某个中国行业标准或私有协议；
- 权威数据与轨迹预测冲突时采用何种优先级；
- 官方灯态在高德全国覆盖中的精确比例。

因此文档中应写“官方灯态接入”，不要未经证据写成“高德通过 SPaT 直连所有信号机”。

## 北斗和实时车流分别做什么

### 北斗/GNSS

北京市科委材料把“北斗定位、人工智能、智慧交通”列为能力组合，并在绿波服务中提到车辆实时位置、路口距离和车流量。结合专利对 GPS/GNSS 轨迹的定义，可以确认定位用于：

- 把车辆轨迹匹配到路口、进口道和转向；
- 识别停车、启动、通过时间；
- 判断当前用户到路口的距离与所在方向；
- 为绿波建议计算车辆当前状态。

“北斗提供灯态”则没有证据。合理解释是北斗属于定位传感器，灯态仍来自官方数据或对车辆行为的统计推断。

### 实时车流

公开材料明确说绿波速度结合车辆当前位置、距路口距离与车流量计算。专利也用当前预测时段中已经产生的轨迹校验变灯时间。因此实时或近实时车流/轨迹会参与服务。

但“当前车流很堵”不能单独告诉系统红灯还剩几秒。它需要先有路口方向、信号周期/偏移或官方灯态，再结合当前车辆位置提供倒计时、等待轮次或绿波速度。

## “主要靠数据量学习”应该怎样准确表述

### 已证实

- 无官方覆盖时，多车轨迹是公开方案的核心数据源。
- 多天、同路口、同时段的样本用于寻找周期性和估计变灯偏移。
- 低流量会天然让周期峰值、停车分布和当前校验更不稳定；专利的设计本身依赖足够样本形成可识别分布。
- 模型不是唯一算法：直方/数量分布、峰值周期、拐点、聚类、异常过滤和时序预测共同组成管线。

### 官方或申请人的效果表述，不能当独立评测

- 专利声称其方案提高准确度、覆盖面、泛化性和实时性。
- 官方宣传称倒计时能“预判秒级变化”、日服务次数超过 20 亿。

这些能证明产品定位和申请人主张，不能代替公开的路口级 MAE、误差分布、夜间表现或不同数据源消融实验。

### 合理推断

- 高德很可能按路口、方向、时段和数据可用性选择或融合官方灯态与轨迹推断，而不是全国只有一个数据路径。
- 有权威实时灯态时，它通常应比纯历史周期推断更直接；轨迹仍可用于校验、补覆盖和检测异常。
- 浮动车数量越多通常越容易观察周期，但重复、错误地图匹配、非灯控停车和时段变化不会仅靠“更多行”自动消失，所以清洗与事件定义和样本量同样重要。

### 未知

- 线上模型的具体架构、参数、训练窗口和更新间隔；
- 是否采用贝叶斯更新、Kalman filter 或其他在线滤波；
- 高德当前产品如何融合官方灯态、预测与实时轨迹；
- 生产准确率以及产品显示/隐藏倒计时的质量阈值；
- 用户手机、车机、网约车或其他车队各自贡献了多少轨迹。

## 对 CUHK 校巴 ETA 的可迁移启示

红绿灯案例支持“从大量简单行为事件中学习规律”，但不能直接证明“不需要匹配 Trip”。两者的物理过程不同：

| 红绿灯                               | CUHK 校巴                                                  |
| ------------------------------------ | ---------------------------------------------------------- |
| 通常在一个时段内重复固定或近固定周期 | 发车可提前、延迟、跳班或临时加班                           |
| 大量车辆都受同一个信号相位控制       | 一条反馈通常来自某一辆巴士                                 |
| 可从成批停车/启动的周期峰值恢复相位  | 只有“线路、站点、到站时间”时，班距短处可能对应多个候选班次 |
| 每个周期会产生许多车辆轨迹           | 每班每站最多只有一次物理到站事件                           |

真正可迁移的是工程模式：

1. **原始观测与物理事件分开**：所有用户点击都保存，但同一辆巴士同一次到站应聚合为一个 `ArrivalEvent`，类似高德从多条车辆轨迹提取一个信号切换事实。
2. **按条件分层学习**：路线模式、站点、时段、教学日、`weekOfTerm` 是校巴版本的“路口、方向、时段”。
3. **历史层与在线层分开**：历史事件学习长期 ETA；当天新事件可以校验或修正当前运行状态。
4. **不确定时不要强行归属**：校巴若无法高置信匹配某个 `Trip`，仍可用于站点/时段总体分布，但不应把延误传播到某一班下游。
5. **多数据源按来源标注**：官方发车计划、人工测量、用户到站反馈与未来车辆 GPS 各自保留 provenance，不能混成同一种“真实时间”。

高德的规模优势也提示一个边界：它能从同一路口的海量车辆恢复很弱的周期信号；CUHK 校巴反馈量远小，不能因为采用相同概念就预期同样收敛速度。对校巴来说，简单的层级统计/贝叶斯收缩和明确回退可能比大模型更合适，是否实时修改当前班次仍需用本项目数据验证。

## 开源结论

本次没有找到高德为红绿灯倒计时发布的开源实现。上述专利给出了可复现思路，但：

- 专利授权不是开源许可证；
- 专利权利要求可能带来实施许可问题；
- 公开文字缺少生产阈值、训练数据和质量 gate；
- 即使自行重写，也不能称为高德线上实现。

如果下一步要找可直接试验的开源算法，应另查“traffic signal timing inference from probe trajectories / floating car data / phase change estimation”的论文代码，并优先选择许可证明确、有合成或公开数据集、能表达观测不确定性的实现；不能把高德专利页面当作代码依赖。
